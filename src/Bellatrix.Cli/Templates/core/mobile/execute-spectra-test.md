# Execute SPECTRA Test Cases via the bellatrix mobile CLI

Automatically execute SPECTRA manual test cases by driving a live Android or iOS app through the
`bellatrix mobile` CLI. Each test step is performed through UI automation and the expected result is
validated against what the app actually shows. Results are reported back to SPECTRA for tracking. No code
is generated by this skill (for code, use `bellatrix-mobile-automate-spectra-test`).

**Two surfaces used:**
- `bellatrix mobile` CLI — UI interaction (snapshot, find, click, type, read, gestures, app control)
- `spectra/*` tools — test execution state (start run, read test, advance test, finalize)

Appium and the device/emulator/simulator are the user's to run. Never start, stop, or probe them; on a
connection error, ask the user to start them and retry.

---

## Trigger Phrases

- "execute TC-205 via the bellatrix mobile CLI"
- "run TC-100 through TC-110 on Android automatically"
- "auto-execute the login suite on the iOS simulator"
- "run this test case through the app"
- "smoke-test the app with the SPECTRA cases"

## Workflow

### Step 1: Start SPECTRA Execution Run

```
Tool: start_execution_run
Params: { "suite": "{suite_name}" }  or  { "test_ids": ["TC-205", "TC-206"] }
```

Record the `run_id` and `test_handles` from the response.

### Step 2: Start the BELLATRIX Mobile Session

```
bellatrix mobile start-session --platform android --app "<path to .apk>" --session run1 --json
bellatrix mobile start-session --platform ios --app "<path to .app/.ipa>" --session run1 --json
```

{{> lang:app-path}}

### Step 3: Capture Initial UI Snapshot (MANDATORY)

```
bellatrix mobile snapshot --session run1 --json
```

Returns only `{ path, elementCount, summary }`. Never read the snapshot file or `get-page-source` output
into this context — resolve locators through the **`bellatrix-mobile-locator-specialist`** subagent
(pass the step description + snapshot `path` + platform) or with a narrow
`bellatrix mobile find --session run1 --snapshot <path> --resource-id|--content-desc|--text|--class|--grep … --json`.

### Step 4: For Each Test Case

#### 4a. Read Test Details from SPECTRA

```
Tool: get_test_case_details
Params: { "test_handle": "{handle}" }
```

Extract **Preconditions**, ordered **Steps**, and the **Expected Result**.

#### 4b. Execute Preconditions

If preconditions require UI actions (e.g. "user is logged in", "cart contains one item"), perform them
via the CLI, then snapshot to confirm the app is in the expected state. If a precondition cannot be met,
mark the test BLOCKED with the reason.

#### 4c. Execute Each Step

Interpret each natural-language step and map it to CLI calls (every element verb takes
`--strategy <t> --locator <v>`):

| Step pattern | `bellatrix mobile` command | Example |
|-------------|----------------------------|---------|
| "Tap / Press {control}" | `click` | `click --session run1 --strategy accessibilityid --locator "Log in" --json` |
| "Enter / Type {text} in {field}" | `type-text` | `type-text --session run1 --strategy id --locator "com.example.shop:id/username" --text "demo.user" --json` |
| "Clear {field}" | `clear` | `clear --session run1 --strategy id --locator "com.example.shop:id/search" --json` |
| "Verify {text} is shown" | `get-text` / `is-visible` | `get-text --session run1 --strategy id --locator "com.example.shop:id/welcome" --json` |
| "Verify {option} is checked / on" | `get-attribute` | `get-attribute --session run1 --strategy id --locator "com.example.shop:id/remember" --attribute checked --json` |
| "Verify {button} is disabled" | `is-enabled` | `is-enabled --session run1 --strategy accessibilityid --locator "Pay" --json` |
| "Select {option} from {drop-down}" | `click` ×2 | tap the spinner/picker, re-`snapshot`, tap the option |
| "Scroll to {item}" | `scroll-to-element` | `scroll-to-element --session run1 --strategy accessibilityid --locator "Checkout" --json` |
| "Swipe {direction}" | `swipe` | `swipe --session run1 --start-x 900 --start-y 1200 --end-x 100 --end-y 1200 --json` |
| "Put the app in background for N s" | `background-app` | `background-app --session run1 --seconds 5 --json` |
| "Rotate to landscape" | `set-orientation` | `set-orientation --session run1 --orientation landscape --json` |
| "Close / reopen the app" | `close-app` / `launch-app` | `launch-app --session run1 --app-id com.example.shop --json` |
| "Open the web content" | `get-contexts` / `set-context` | `set-context --session run1 --context WEBVIEW_com.example.shop --json` |

**After each step:** re-`snapshot` if the screen changed (navigation, dialog, sheet, keyboard, scroll) or
the next step targets a different area — locators must come from the CURRENT snapshot.

**If a step fails** (element not found, tap has no effect): snapshot, take a screenshot
(`take-screenshot --out <file>`), mark the test FAILED with the failing step, and move to the next test.

#### 4d. Validate the Expected Result

1. Read the element(s) that should reflect the outcome (`get-text`, `is-visible`, `get-attribute`)
2. Compare the actual value with the expected result — exact text unless the test case says "contains"
3. Determine the verdict:

| Comparison | Verdict |
|-----------|---------|
| Actual matches expected | PASS |
| Actual differs from expected | FAIL |
| Element not found | FAIL |
| App crashed, closed, or a system dialog blocks it | BLOCKED |

#### 4e. Report Result to SPECTRA

```
Tool: advance_test_case
Params: {
  "test_handle": "{handle}",
  "status": "PASSED|FAILED|BLOCKED",
  "notes": "Step 3: expected 'Welcome, demo.user' but got 'Welcome back'. Screenshot: tc205-step3.png"
}
```

For FAILED tests include the failing step, expected vs actual, and the screenshot file.

#### 4f. Reset App State

Before the next test, return the app to a clean starting state:
- Navigate back to the start screen, or
- `close-app --app-id <id>` then `launch-app --app-id <id>`, or
- if the app is wedged: `close-session`, then `start-session` again under the same name

Then re-`snapshot`.

### Step 5: Close Session and Finalize

```
bellatrix mobile close-session --session run1 --json
bellatrix mobile list-sessions --json
```

```
Tool: finalize_execution_run
Params: { "run_id": "{run_id}" }
```

Then open the HTML report:

```
show preview .execution/reports/{html_filename}
```

### Step 6: Present Summary

```
Execution Complete
══════════════════════════════════

  Suite: Login (Android)
  Tests: 12
  Passed: 10
  Failed: 1
  Blocked: 1

  Failed tests:
    TC-205: Step 3 — expected "Welcome, demo.user" but the label showed "Welcome back"

  Blocked tests:

  Report: .execution/reports/run_2026-04-12_001.html
```

## Error Handling

| Error | Action |
|-------|--------|
| Cannot reach Appium / no device | Stop; ask the user to start Appium and boot the device; retry |
| Element not found | Snapshot, try an alternative locator from the specialist; still missing → FAIL "Element not found: {strategy} {value}" |
| App not responding | Wait 10s, retry once; still unresponsive → BLOCKED |
| App crashed / closed | BLOCKED for the current test; `launch-app` (or restart the session) for the remaining tests |
| System dialog (permissions, keyboard, rate-the-app) | Snapshot, dismiss it if a step allows; if blocking → BLOCKED |
| Wrong context (WebView vs native) | `get-contexts`, `set-context` to the right one, retry |
| Session not found | `start-session` again with the same `--session` name |

## Mode Selection

When the user asks to execute tests, ask which mode:

```
How should I execute these tests?

1. Auto-execute via the bellatrix mobile CLI — I drive the app on the device,
   validate results, and report pass/fail (hands-free)

2. Assisted execution — I show each step and wait for you to confirm the
   result manually on the device (you watch, I track)
```

**Mode 1 (Auto):** the workflow above.

**Mode 2 (Assisted):** show each step, wait for the user to say pass/fail. Uses only SPECTRA — no CLI.

## Tips

- **Batches:** for large suites run 10–20 tests per batch so one early failure doesn't cascade
- **Screenshots:** capture one on every FAIL — always with `--out <file>` so the image never enters context
- **Flaky steps:** if a test fails on the first attempt, offer one retry before marking it FAILED
- **New screens:** snapshot each new screen, dialog, or sheet before interacting with it
- **Always close:** call `close-session` at the end, even after failures or interruptions
